## Production RLS snapshot before changes

A read-only catalog query recorded RLS, policies and grants before creating the
hardening migration. RLS is enabled on all five beta-critical tables:

- `profiles`
- `favorites`
- `season_planner_events`
- `events`
- `user_feedback`

Ownership predicates use `auth.uid()` for profiles, favorites, planner rows and
submitted events. Profile update policies include `WITH CHECK`; Season Planner
updates include both `USING` and `WITH CHECK`. Event approval/update/delete and
feedback administration require `private.is_admin()`.

The live anonymous PostgREST audit passed:

| Dataset | Result |
| --- | --- |
| Approved events | HTTP 200, one public row requested and visible |
| Pending events | HTTP 200, zero rows |
| Profiles | HTTP 401 |
| Favorites | HTTP 401 |
| Season Planner | HTTP 401 |
| Feedback | HTTP 401 |
| Analytics | HTTP 401 |

This is strong evidence for anonymous isolation, but it is not proof of
cross-user isolation in production. The latter still requires two production
accounts and one admin.

## Local Auth/RLS verification

After a clean local database reset applied all migrations including the new
`20260814120000_beta_security_definer_hardening.sql`, the integration suite created
temporary User A, User B and Admin accounts, ran 20 cases and removed the
accounts afterward.

Result: **20/20 passed**. Covered outcomes include:

- own-profile and anti-role-escalation boundaries;
- User A/User B favorite and Season Planner isolation;
- pending submission creation and denial of self-approval;
- admin review and event update;
- private operations/Stage-4 datasets;
- service-role-only worker paths;
- denial of five admin RPCs to a normal user;
- invalid anonymous cron secret returns false;
- Stage 4 remains dry-run, inactive, private and theoretical.

The local Advisor completed with no error-level finding. Remaining informational
performance notices concern unindexed foreign keys and unused indexes, mainly
in the not-yet-deployed Stage-4 schema; they are not a reason to alter indexes
without workload evidence.

## Critical finding and local fix

Production currently grants `authenticated` execution of
`run_event_validation(bigint, uuid)`. Before hardening, the function was
`SECURITY DEFINER` and did not check admin/service status. Nullable parameters
could scope its updates across all matching validation issues.

The new migration adds an admin-or-service check before any parameter use,
function call or update. The production database is deliberately unchanged;
the fix must be deployed through a separate reviewed migration deployment.

Until that deployment and a post-deployment negative test are complete, the
production security gate is **NO-GO**.

## Password security

The production organization is on the Supabase Free plan. Current Supabase
documentation states that leaked-password protection is available on Pro and
above, and the production Advisor confirms that it is disabled.

| Risk | Impact | Interim measure | Owner | Recheck |
| --- | --- | --- | --- | --- |
| Known-compromised passwords are not rejected by Supabase | Credential-stuffing probability is higher for reused passwords | Minimum 8 characters, instruct testers to use unique password-manager-generated credentials, keep beta small, monitor Auth anomalies, upgrade before broader rollout | Product operator | Before increasing beyond 20 testers or by 2026-09-01, whichever comes first |

This is an accepted Beta risk only if the operator signs off. No workaround was
used and no setting was changed.
